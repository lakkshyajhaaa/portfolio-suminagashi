## Overview

LibreCube is an international open-source initiative developing standardized hardware and software architectures for space exploration, CubeSats, and satellite ground stations. Mission operations in modern space infrastructure frequently leverage **Yamcs**—a battle-tested open-source mission control and telemetry processing system.

However, a major workflow gap existed: spacecraft telemetry schemas are officially documented using the standard **XTCE XML** (XML Telemetric & Command Exchange) schema, whereas Yamcs mission control setups rely on structured multi-sheet spreadsheets (Excel 97-2003 `.xls`). Manually translating hundreds of telemetry parameters into spreadsheets was tedious, error-prone, and prevented automated CI/CD mission database validation.

---

## 01. The Problem

1. **Manual Ingestion Friction:** Aerospace engineers had to hand-craft spreadsheets for every telemetry and command definition, risking flight-critical data transposition errors.
2. **Schema Incompatibility:** XTCE XML utilizes complex hierarchical schemas with nested parameter types, calibration polynomials, and container inheritance that do not natively map to flat spreadsheet cells.
3. **Automated Testing Blockers:** Without programmatic conversion, satellite ground software pipelines could not automatically rebuild their mission databases upon telemetry updates.

### Who Experiences This Problem?
Aerospace engineers, ground station operators, and satellite developers configuring Yamcs mission control systems for CubeSat missions.

As an independent open-source contributor to LibreCube, I engineered and contributed the end-to-end conversion utility:

- **Authored `convert_xtce.py`:** Developed a robust Python utility utilizing `xml.etree.ElementTree` to parse XTCE XML documents, recursively resolving namespaces, parameter declarations, units, bit lengths, and command arguments.
- **Dynamic Spreadsheet Generation:** Implemented multi-sheet Excel generation using `xlwt`, structuring distinct sheets for `Parameters`, `Commands`, `Arguments`, `Containers`, and the mandatory `General` configuration sheet required by Yamcs.

- **Upstream Merge:** Packaged clean documentation, test fixtures, and submitted a Merge Request that was reviewed, approved, and merged into the upstream repository.

## 04. Engineering Challenges & Trade-offs

### Challenge 1: XTCE Namespace and Inheritance Resolution
- **Constraint:** XTCE specifications allow nested container inheritance (where packet headers inherit base packet definitions) and dynamic namespace declarations across different satellite manufacturers.
- **Alternative Considered:** Regex-based string parsing. This proved too brittle and failed on well-formed but differently indented XML documents.
- **Selected Approach:** Built an AST-like recursive crawler with `xml.etree.ElementTree` that dynamically strips XML namespaces and traverses container inheritance trees to accurately compute packet byte offsets.

### Challenge 2: Adherence to Legacy Binary `.xls` Format
- **Constraint:** Modern Python tools default to `.xlsx` (OpenXML), but the Yamcs engine's spreadsheet parser strictly required the legacy binary Excel 97-2003 `.xls` format.
- **Resolution:** Integrated the `xlwt` library, managing cell styling, data types, and multi-sheet generation strictly within the legacy binary format constraints to guarantee compatibility with Yamcs internal loaders.
