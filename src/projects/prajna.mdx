## Overview

Most computer vision and facial verification models operate as unconditional classifiers: when presented with an input image, they generate an embedding and force a hard identity prediction, regardless of ambient illumination, occlusion, or epistemic uncertainty. In high-stakes identity verification, this unconditional paradigm leads to overconfident misclassifications and high compute waste.

**Prajñā** introduces a **responsibility-aware AI inference framework**. Instead of treating predictions as binary truths, the system evaluates composite image quality, cosine confidence, and identity ambiguity to decide whether a prediction deserves to be accepted immediately, escalated to a secondary compute tier, flagged for human-in-the-loop audit, or rejected before consuming downstream resources.

---

## 01. The Problem

Automated facial verification systems in production environments face three fundamental engineering bottlenecks:

1. **Compute Inefficiency:** Running heavy deep-learning feature extractors (e.g., 512-dimensional ResNet backbones) on low-quality, blurry, or trivially obvious inputs wastes computational budget and increases end-to-end latency.
2. **Uncalibrated Overconfidence:** Conventional neural networks frequently output high-probability predictions on out-of-distribution or degraded samples because their softmax or cosine outputs lack epistemic uncertainty awareness.
3. **Server-Side Biometric Centralization:** Traditional architectures maintain centralized relational databases storing sensitive biometric vectors and raw photos, creating persistent honeypots vulnerable to data breach and regulatory compliance liabilities.

### Who Experiences This Problem?
Security engineers, identity platforms, and automated verification workflows that must process high volumes of verification requests reliably without ballooning GPU inference costs or centralizing sensitive biometric data.

## 03. System Architecture & Decision Pipeline

Prajñā structures verification through a deterministic five-phase decision pipeline:

```text
Input Image
   │
   ▼
[Phase 0: Quality Gate] ──(Q < 0.20)──► HARD REJECT (Insufficient Quality)
   │ (Q ≥ 0.20)
   ▼
[Phase 1: Stage-1 Inference] (MobileFaceNet, 128-d)
   │
   ▼
[Phase 2: Uncertainty Evaluation] 
   │  - Cosine Confidence (R)
   │  - Quality Attenuation φ(Q)
   │  - Prediction Margin / Ambiguity ψ(A)
   │  - Routing Score: ρ = R · φ(Q) · ψ(A)
   │
   ├──(ρ ≥ ρ_accept)──────► ACCEPT (Instant Resolution, Low Compute)
   ├──(ρ ≤ ρ_reject)──────► REJECT (Definitive Non-Match)
   │
   ▼ (Escalation Band: ρ_reject < ρ < ρ_accept)
[Phase 3: Stage-2 Deep Scan] (InceptionResnetV1, 512-d)
   │
   ├──(High Precision Match)──► ACCEPT (Resolved via High-Compute)
   ├──(Definitive Non-Match)──► REJECT
   └──(Persistent Ambiguity)──► HUMAN-IN-THE-LOOP REVIEW
```

### The Mathematical Routing Engine

The routing engine computes a composite confidence score `ρ ∈ [0, 1]` before deciding whether to finalize or escalate:

```text
ρ = R · φ(Q) · ψ(A)
```

Where:
- **R (Responsibility Score):** Cosine similarity between client embedding vector and candidate identity vector, normalized to `[0, 1]`.
- **φ(Q) = Q^κ (Quality Attenuation):** Attenuates confidence based on composite image quality `Q ∈ [0, 1]` (evaluating Laplacian variance for sharpness, luminance histogram, and resolution). Default exponent `κ = 0.50`.
- **ψ(A) = 1 - λ · A (Ambiguity Attenuation):** Penalizes predictions when the ratio between the top-2 candidate similarity and top-1 candidate similarity is high (`A = S_top2 / S_top1`). Default penalty weight `λ = 0.30`.

## 04. Security, Privacy & Threat Model

Biometric systems require rigorous technical transparency regarding data handling and privacy boundaries.

### Data Handling Architecture
- **Information Collected:** During verification, the browser captures a single facial image frame from the user's local camera.
- **Local Storage:** Upon enrollment, mathematical feature embeddings (128-d float array) are returned to the user's client and stored in the browser's `localStorage` as a client-held credential. Raw facial photographs are never stored on disk by either client or server.
- **Transmission:** The verification request transmits the current image frame and client-held embedding token over TLS/HTTPS to the FastAPI verification endpoint.
- **Server Processing:** The server processes the request entirely in volatile memory (RAM). The image is decoded, embeddings are extracted, similarity is calculated, and routing thresholds are evaluated.
- **Data Retention:** Ephemeral in-memory execution. All image buffers, tensors, and intermediate embedding matrices are freed immediately upon request completion. The server maintains **zero persistent database of facial photographs or biometric templates**.

### Threat Model & Limitations
1. **Client Storage Boundary:** `localStorage` is accessible to client-side scripts. In a production untrusted environment, an XSS vulnerability could expose stored embedding vectors. Production enterprise deployments would require migrating token storage to WebAuthn / FIDO2 hardware-backed cryptographic keystores.
2. **Stateless vs. Zero-Knowledge Distinction:** Prajñā utilizes a **stateless, client-held token architecture**, not a cryptographic zero-knowledge proof (ZKP). The server does inspect the client embedding in memory to perform vector dot products; privacy is achieved through stateless ephemeral execution and non-retention rather than cryptographic homomorphic encryption.
3. **Transport Security Dependency:** Privacy guarantees assume an encrypted HTTPS transport channel to protect vectors and images against network-layer interception.

## 05. Engineering Challenges & Trade-offs

### Challenge 1: CPU Latency on Containerized Cloud Environments
- **Constraint:** Public cloud deployment on Hugging Face Spaces operates within constrained CPU resources (2 vCPUs) without dedicated GPU acceleration. Running InceptionResnetV1 on every single frame yielded latencies of 1.2–1.8 seconds.
- **Alternative Considered:** Downscaling images prior to single-model inference. While this reduced latency, it degraded fine-grained verification accuracy on edge cases.
- **Selected Approach:** The two-stage hierarchical quality and routing gate. 70%+ of unambiguous matching and non-matching requests are terminated at Stage 1 (MobileFaceNet) in under 80ms, reserving the heavier 512-d model strictly for the ambiguous escalation band.

### Challenge 2: Calibration of Uncertainty vs. False Rejections
- **Trade-off:** Setting aggressive quality gates (`Q`) prevents false matches on degraded inputs but risks rejecting legitimate users under poor lighting.
- **Resolution:** Decoupled the hard quality gate (`Q < 0.20` hard reject) from the continuous quality attenuation factor `φ(Q)`. Moderately underexposed inputs (`0.20 ≤ Q < 0.60`) are not rejected outright; instead, their routing score `ρ` is penalized, routing them to the high-capacity Stage 2 model where deeper feature representations can resolve ambiguities.

## 06. Validation & Results

- **Latency Profile (CPU Benchmark):**
  - Phase 0 Hard Rejection: under 15 ms
  - Stage 1 Resolution (Accept/Reject): 65 ms - 95 ms
  - Stage 2 Escalation (Deep Scan): 450 ms - 720 ms
- **Compute Reduction:** Evaluated across synthetic test sets with varied image quality distributions; early exit routing eliminated Stage 2 compute for approximately 72% of high-confidence queries.
- **Interactive Validation:** Live deployment hosted publicly on Hugging Face Spaces with real-time routing decision logs and identity distance metrics.
