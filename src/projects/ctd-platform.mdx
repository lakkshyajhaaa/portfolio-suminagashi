## Overview

Managing academic training schedules, student records, and verified physical attendance across an institution with thousands of students presents significant operational hurdles. Manual paper sign-in sheets and static QR codes suffer from pervasive proxy attendance, data entry latency, and administrative bottlenecks.

During my software engineering internship with the Centre for Training & Development (CTD) at Thapar University, I owned the full-stack design and delivery of an institutional platform engineered to replace manual roll-calls with a secure, highly-concurrent digital workflow.

---

## 01. The Problem

Prior to platform deployment, institutional session management encountered several points of failure:

1. **Proxy Attendance Vulnerabilities:** Students routinely shared static attendance links and codes over messaging apps to mark absent peers.
2. **Concurrent Peak Surges:** At the conclusion of lecture sessions, hundreds of students concurrently attempt to verify attendance within a tight 1-to-2 minute window, overwhelming naive database connections.
3. **Fragmented Records:** Session notes, attendance percentages, trainer schedules, and student progress metrics lived in disconnected spreadsheets, hindering institutional oversight.

### Who Experiences This Problem?
University administrators, academic trainers managing multiple cohort schedules, and students requiring real-time visibility into their session credits and attendance thresholds.

## 03. System Architecture

The platform is architected around an event-driven session verification workflow:

```text
[Trainer Dashboard] 
   │ Initiates Session Verification
   ▼
[Server: Ephemeral Code Engine]
   │ Generates rotating 6-digit code (TTL: 20s)
   │ Stores hash in Redis / in-memory cache with expiry
   ▼
[Trainer Display Screen] ──(Rotates every 20s)──► Physical Lecture Hall
                                                         │
                                        Students enter code via mobile/laptop
                                                         ▼
                                              [Student Web Interface]
                                                         │
                                    POST /api/attendance/verify (JWT Auth)
                                                         │
                                                         ▼
                                              [API Gate: Zod & Rate Limiter]
                                              - Max 5 req/min per user
                                              - Session validity check
                                                         │
                                                         ▼
                                              [Code Verification Service]
                                              - Compares code within valid window
                                              - Checks student cohort enrollment
                                                         │
                                                         ▼
                                              [PostgreSQL Database]
                                              - Atomic AttendanceRecord insertion
                                              - Updates aggregate attendance metrics
```

## 04. Engineering Challenges & Trade-offs

### Challenge 1: Concurrency Spikes During Session End
- **Constraint:** When a cohort of 400+ students all submit attendance codes within seconds of each other, sudden database connection pool exhaustion caused request queuing and intermittent 504 timeouts.
- **Alternative Considered:** Increasing raw database connection limits. This increased infrastructure cost and strained the relational instance during otherwise idle periods.
- **Selected Approach:** Optimized database operations by implementing indexed queries (`studentId` + `sessionId` compound unique index), validating rate limits and timestamps before issuing database transactions, and leveraging Prisma connection pooling.

### Challenge 2: Combating Code-Sharing Over Messaging Networks
- **Constraint:** Students inside the lecture hall immediately screenshot and message verification codes to absent friends.
- **Resolution:** Reduced the code time-to-live (TTL) to a strict 20 seconds with automatic client refresh. Combined with rate-limiting (blocking accounts after 5 incorrect guesses), the window of opportunity to transmit a code off-site, receive it, and submit it before invalidation was drastically minimized.

## 05. Validation & Results

- **Campus Adoption:** Deployed into production across Thapar University's Centre for Training & Development, supporting **3,000+ registered students** and **40+ active trainers**.
- **System Stability:** Maintained consistent uptime throughout peak campus testing periods and end-of-semester training bootcamps.
- **Administrative Efficiency:** Reduced trainer post-session attendance processing time from an average of 15 minutes per session to instant automated synchronization.
- **Measured Metrics:**
  - Database Query Response Time: `< 45ms` (95th percentile) for verification endpoints under load.
  - Rate Limiter Effectiveness: Zero successful brute-force attempts recorded across production logs.
